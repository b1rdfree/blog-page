# commit-msg

基于实际 diff 归纳改动，用「类型标题 + 编号条目」规范提交信息。适用于本项目的 React 页面、Markdown 文档、旅行 JSON 数据集、动效、构建插件和部署配置。

## 调用方式

| 用户意图 | 行为 |
| --- | --- |
| 单独调用 `/commit-msg`、使用 commit-msg，或未明确区分内容与操作的“生成 commit” | 先整理提交范围和 message，再弹框询问是否创建本地 commit |
| 明确只生成／整理提交信息 | 只输出 message，不暂存、不提交，不弹框 |
| 提交／commit 代码 | 确定范围，生成规范 message，执行本地提交 |
| 给出 message 并要求提交 | 保留原意，按本规范整理格式后提交；若明确要求原样使用，以用户指令为准 |

创建或修改本 skill 本身不表示用户要求提交代码。

## 默认弹框流程

1. 先阅读实际改动，确定拟提交范围并展示完整 message，让用户可以审核具体结果；此时不暂存、不提交。
2. 说明这是本 skill 的默认流程，并链接当前 `SKILL.md`，引用本条规则：“默认使用时，弹框询问是否创建一个本地 commit”。
3. 使用 `request_user_input_async` 弹框，问题为“是否按上方提交范围和信息创建一个本地 commit？”，选项依次为“创建本地 commit”“仅生成提交信息”“取消”。
4. 等待用户明确选择。选择创建后按下文提交流程执行；选择仅生成则输出规范 message；选择取消则结束。预选项、未回答、关闭弹框或超时都不表示同意，不得据此暂存或提交。
5. 若弹框工具不可用，说明限制并在对话中询问同样的选择；不要声称已弹框，也不要使用禁止用于权限确认的工具代替。

用户已经明确要求提交且范围明确时，直接执行，无需重复弹框；明确只要提交信息时直接生成。

## Message 格式

```text
feat:
1.添加旅游行程的预算筛选
2.添加出行清单完成进度展示
fix:
1.修复章节跳转导致 HashRouter 进入 404 的问题
```

- 一个 commit 可以只有一种类型，也可以包含多种类型；同一类型只出现一次，相关条目合并到同一组。
- 类型使用下表中的小写英文，标题严格为 `type:`，使用半角冒号并独占一行；不写 `type: 摘要`，不添加 scope 或独立总标题。
- 每组至少一项，编号从 `1.` 开始连续递增，切换类型后重新从 `1.` 开始；数字与正文之间不加空格，格式为 `1.内容`。
- **每项内容只能占一个物理行**，不得手动折行、添加续行、嵌套列表或多行代码。显示界面的自动折行不算换行。
- 消息由类型行和条目行组成，不插入空白行、额外说明或页脚。仅生成 message 时输出纯文本，不套 Markdown 代码围栏。
- 中文为主，技术名称保留英文，以「添加／修复／优化／移除／更新」等具体动作描述改动及其目的，不加句末句号。
- 按用户可理解的独立改动归纳，不逐文件罗列；同一改动不在多个类型下重复。条目过长时精简措辞，独立改动拆成多项。
- 不使用 `WIP`、`misc`、`update files`、「修改文件」等无信息描述，不编造 diff 中不存在的功能、修复或验证结果。
- 分组按下表顺序排列，只保留实际涉及的类型；组内优先写主要改动。
- 仓库历史可用于了解术语，但历史单行或英文提交风格不能覆盖本规范。

## 类型与项目约定

| 类型 | 用途与本项目示例 |
| --- | --- |
| `feat` | 新增用户能力，如栏目、搜索筛选、行程模板模块、清单交互 |
| `fix` | 修复错误行为，如路由跳转、加载失败、筛选错误、动画卸载异常 |
| `perf` | 性能优化，如正文按需加载、资源预取、缓存、动画帧率优化 |
| `refactor` | 不改变行为的结构整理，如提取公共组件、拆分数据加载层 |
| `style` | 视觉与排版改动，如配色、间距、玻璃效果、响应式布局；明确修复显示缺陷时用 `fix` |
| `docs` | 内容与说明，如 README、Markdown 笔记、旅行 JSON 攻略或清单、注释、`.agents/` 下的 skill 说明 |
| `test` | 测试用例、测试辅助代码 |
| `build` | 构建与依赖，如 Vite、TypeScript 配置、索引构建插件、package.json 依赖及锁文件 |
| `ci` | 自动化流水线，如 GitHub Actions、GitHub Pages 发布和自托管同步步骤 |
| `chore` | 不属于以上类型的维护，如版本号、忽略规则、开发辅助脚本 |

按改动目的分类，不只看文件路径。例如，仅增加一份旅行 JSON 内容用 `docs`；新增一种旅行模块的类型定义和渲染逻辑用 `feat`；为该功能配套的示例数据可与功能归为同一条，不必机械拆组。

## 确定提交范围

1. 阅读 `git status --short`、`git diff --cached` 和必要的 `git diff`；未跟踪文件需要读取正文，不能只凭文件名生成 message。
2. 用户指定了范围时遵循指定范围。否则暂存区非空则以暂存内容为准，不加入其他未暂存改动，保留文件内的部分暂存边界。
3. 暂存区为空时：仅生成 message 可基于工作区改动；要求提交时，只暂存用户已授权的改动。范围明确就继续，存在无法判断是否属于本次提交的改动时才询问范围，不默认 `git add -A`。
4. 没有可归纳或可提交的改动时说明情况并停止，不生成虚构 message 或空提交。

## 提交与验证

用户明确要求提交，或在默认弹框中选择“创建本地 commit”后，执行以下流程：

1. 暂存确定范围后重新阅读 `git diff --cached`，让 message 与最终暂存内容一致。检查类型不重复、每组编号连续、每项单行、没有空分组或额外段落。
2. 展示拟用 message 和提交范围。用户已明确授权本地提交且范围明确时直接执行，不重复要求确认；用户要求先审核时，展示后等待其批准。
3. 将完整 message 以 UTF-8 和真实换行写入临时文件，用 `git commit -F <文件>` 提交并清理临时文件。写文件时使用文件工具或安全的引用方式，不把 message 拼进 shell 命令，不使用 `git commit -m "..."`，避免反引号、`$()`、引号或换行被 shell 解释。
4. 成功后核对新提交 SHA、`git show -s --format=%B HEAD`、提交文件清单和 `git status --short`，确认实际信息和范围符合预期。简要报告 SHA、message 与是否有剩余改动。
5. 提交失败时报告错误及实际暂存区／工作区状态，不声称成功，不自动绕过 hook，不自动重试或恢复文件。不执行 push，除非用户另外明确要求。

## 混合类型示例

以下仅演示格式，实际条目必须从本次 diff 归纳：

```text
feat:
1.添加旅游行程的节奏与预算筛选
fix:
1.修复切换文档后保留上一篇滚动位置的问题
perf:
1.拆分文档元数据与正文以减少首页加载体积
style:
1.统一文档页与旅游页的深色玻璃背景
docs:
1.补充广西旅游总览中的交通说明
2.添加项目提交信息规范
ci:
1.为自托管部署添加 DEPLOY_ENABLED 开关
```
